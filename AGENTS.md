# Working on claude-mods

- Each top-level folder is one Claude Code mod, a plugin of function hooks: `.claude-plugin/plugin.json`, `hooks/hooks.json` naming `hooks/register.tsx`, its state contract in `types/index.d.ts`, tests in `tests/`. The plugin-authoring skill holds the API and its types.
- `.claude-plugin/marketplace.json` lists every mod. `make install` adds this folder as the `claude-mods` marketplace and installs each listed mod at user scope, so every session loads it. Installing writes `enabledPlugins` and the marketplace into `~/.claude/settings.json`, which is a link into `~/dotfiles`.
- An installed mod is read from this folder, not from a copy: after an edit, `/reload-plugins` in a running session loads it. No reinstall, no version bump.
- To add a mod: write it with the plugin-authoring skill, where it hot-reloads in that session, then move its folder here without `.claude-plugin/types/`, add it to `marketplace.json`, and run `make test` and `make install`.
- `make test` runs `claude plugin validate` on the marketplace and each mod, then each mod's `claude plugin test`.
- The engine lays the API's types in `<mod>/.claude-plugin/types/` (ignored) only when it loads the mod from a folder it hot-reloads. The mod's `tsconfig.json` extends them, so `tsc -p <mod>` works only after such a load.
- `$` may be passed only to functions declared at the top level of the hooks module: `claude plugin validate` refuses a helper defined inside `register`.
- The main model reads a mod's slash command as a record: `<command-name>/x</command-name>` with its arguments. To keep the arguments out, an outer `command.run` hook keeps them and passes `next` empty `args`; the hook beneath answers from what it kept (see `aside`).
- Running `claude -p` from an agent's shell to try a mod needs `CLAUDECODE`, `CLAUDE_PID`, `CLAUDE_EFFORT` and `CLAUDE_CODE_*` unset; `--plugin-dir <copy>` loads it. There is no prompt box under `-p`, so `$.prompt.fill` answers `isFilled: false`.

## prompt-enhancer

- ✨ Enhance in the band above the prompt box, or `/enhance <prompt>`, rewrites the draft in place; Send submits the box, Undo puts the draft back. Enter is untouched.
- The rewrite is a `$.model.fork` over the session, so it reads the system prompt, instruction files, skills and the whole chat. Before the session's first turn there is nothing to fork: it reads the CLAUDE.md and AGENTS.md files from the project root up, plus the non-built-in commands, and calls `$.model.complete` on the session's model.
- The rewrite rules live in `hooks/enhance.ts`. A prompt sent with Send goes through `$.prompt.submit`, which does not expand `@file` mentions, so the rules ask for plain paths.

## aside

- `/aside [question]` opens the Aside pane, docked beside the transcript in fullscreen, and asks there; the pane's field takes follow-ups in the same thread. `/btw` is a built-in, so the command can't take that name.
- Each question is a `$.model.fork` over the main conversation, with the side thread's earlier exchanges in the prompt, so nothing is added to the main conversation. The main model sees only `/aside` with empty arguments. A spike on 2026-10-26 confirmed both.
- Questions run on a `$.clock.after` timer, so the command and the field return at once. The thread lives in `$.state` for the session; `/clear` empties it.
- Hand off and `/aside-handoff` fork the same way with the answered exchanges and write a request in the person's voice; `$.prompt.fill` puts it in the box (appended after a draft), never submitted. No call moves the keys from a pane to the prompt box: the person presses Esc.

## prompt-style

- On the terminal, a `UserMessage` row from `composer` (typed here, and still so on resume) or `bridge` (Remote Control) is drawn beside a one-column `claude` bar with no background, in place of the engine's full-width `userMessageBackground` band. Every other row, and every other surface, goes to `next`.
- The engine raises no `UserMessage` for a slash command's echo (`❯ /reload-plugins`) or for a prompt a plugin submits, `asUser` or not (prompt-enhancer's Send), so those keep the band. A spike on 2026-10-26 confirmed both.

## transcript

- `/transcript` writes the chat as Markdown to `$TMPDIR/claude-transcripts/transcript-<first 8 of the session id>.md`, rewritten each run, then runs `mado action -s $MADO_SESSION edit-file <file> <line>`. Mado opens the session's editor (nvim unless set otherwise) on it in its enlarged float, at the newest prompt's heading. Outside a Mado pane it writes the file and says where. The command is `immediate`, so it runs mid-turn.
- The rows come from `$.session.messages()`: at most the newest 4096, with no timestamps. After a compaction the earlier turns are one summary row: a spike on 2026-10-26 confirmed this on a resumed session. `hooks/markdown.ts` drops the rows the engine writes as user text (command output and its caveat, a skill's body, task notifications, system reminders) by their openings, and this command's own records.

## prompt-jump

- `/jump` (`immediate`) opens the `prompt-jump` pane with `focus` and `closeOnEscape`: an Input that filters the prompts typed in this chat, newest first, each drawn `#N HH:MM` and the line holding the query's first word, the first nine with a digit hotkey. Enter in the field picks the first match; ↓ walks to the others. A pick closes the pane, then `$.ui.scroll({ to: { requestId }, block: 'start' })` puts the prompt's row at the top of the chat. Outside fullscreen the command only says so in a toast, as the main screen doesn't scroll.
- A `UserMessage` row's `requestId` is its message's uuid: the id `session.append` hands a hook and the transcript file stores. `$.ui.scroll` reaches the row from a Button press, a field's Enter or a typed command, and closing the pane first leaves the row in place at the full width. A pty spike on 2026-10-29 confirmed all of it in fullscreen.
- `$.session.messages()` rows carry no ids, and `session.append` sees no row a `--resume` loads, so the ids come from the transcript file, `<CLAUDE_CONFIG_DIR or ~/.claude>/projects/<project>/<session id>.jsonl`: the session's cwd and root, made folder names, are tried for `<project>`, then every project folder. `$.fs.read` and `$.process.run` each copy at most 4 MiB, so `grep -F '"origin":{"kind":"human"}'` picks out the typed prompts' rows (no other row carries it: `turnOrigin` is a plain string), and `hooks/prompts.ts` parses those, skipping meta rows, tool results, slash-command records and subagent rows. The file's format is not API.
- The list keeps the prompts `$.session.messages()` still holds, matched by text (whitespace ignored) newest first. A resumed compacted session draws only the turns after the compaction, and lists only their prompts; a `/compact` in a running session leaves the earlier rows on screen, and in the list, and a jump to one works. The same spike confirmed both.
- In `claude plugin test`, `$.ui.scroll` to a transcript row has no implementation (a test's `on('ui.scroll')` is never asked) and rejects. `jump` turns a rejection into the same toast as a deny, which the tests read for the prompt's number.
- On a result Button, a printable key that isn't a hotkey moves the keys to the prompt box, as in walkthrough. `focus` is granted only over an empty prompt box, so with a draft there the pane opens without the keys.
- `/jump-reply` (`immediate`, no pane) scrolls to the start of the newest text Claude wrote, the end of a turn after its tool calls. The transcript file stores each block of a reply on a row of its own, so `grep -F '"role":"assistant","content":[{"type":"text"'` picks out the text rows, and `lastReply` takes the newest that isn't a subagent's, an API error (`isApiErrorMessage`) or an engine stand-in (model `<synthetic>`). An `AssistantMessage` row's `requestId` is that row's uuid, as for a prompt. A pty spike on 2026-10-29 with the installed mod confirmed it: after a turn of thinking, a Bash call and a list, `/jump-reply` and `ctrl+x l` (bound in `~/.claude/keybindings.json`) each put the list's first line at the top of the chat, under the engine's pinned prompt header; the key worked over a draft, which stayed as it was. Its tests read the same toast for a rejected scroll.

## idea-shelf

- `/idea <text>` saves an idea; `/idea` alone and `/ideas` open the shelf, a pane listing the project's ideas newest first, with a field to add one and Remove on each. Both commands are `immediate`. Like `aside`, an outer `command.run` hook keeps the text and passes `next` empty `args`, so the main model sees `/idea` alone. A save is confirmed by a toast, not command output, which would reach the model.
- The ideas live in `$.store` under `ideas:<root>`, where the root is `$.session.repo().root` (the main working tree's for a worktree, so a repo's worktrees share a shelf), else `$.session.root()`. Each change reads the key again just before writing it, and changes run one at a time, so ideas saved meanwhile by another session or by a second save are kept. `$.state` holds only what the pane draws, read from the store each time the pane opens.
- In `claude plugin test`, the test's own `$` has no `store`, and a hook that throws is skipped rather than failing the call: the tests answer `store.*` themselves, and refuse a write with `{ deny }`.

## task-board

- The agent keeps the board through four tools, `mcp__task-board__add_tasks`, `update_tasks`, `remove_tasks` and `list_tasks`, registered at `session.start` with `isDeferred: false` so their schemas are in every session's prompt. Their descriptions are what make the agent use them: add each step while planning, in_progress on start, done on finish, and owner `user` for a step its tools can't take. Each answers with the whole board as text, or `{ deny }` saying why nothing changed (a bad input, an id the board lacks). A `claude -p` spike on 2026-10-27 confirmed the agent does this unprompted and hands the person their step.
- A task is `{ id, title, detail?, owner: 'agent' | 'user', status: 'todo' | 'in_progress' | 'done' }`; ids count up per project (`next` in the stored value), so both sides can say #3. The board lives in `$.store` under `tasks:<root>`, the root found and the writes serialised and re-read as in idea-shelf.
- `/board` opens the pane (`/tasks` is a built-in): in progress, to do, then done newest first, with Start / Done / Reopen and Remove on each task, Clear done, and a field that adds a task of the person's own. A toast tells the person when the agent adds a task as theirs or hands one over; their own changes in the pane raise none, and the agent learns of them only by reading the board again.

## paste-thumbnails

- The API gives a mod no pasted image's bytes while it sits in the box: hooks see only the `[Image #N]` tag, which a paste puts in with a `prompt.change` of origin `engine` (not `prompt.edit`). `$.prompt.media` reads bytes only inside `prompt.submit`, and only for a mod installed by managed settings; a user-scope install is refused.
- So the mod reads the file Claude Code saves the moment an image is pasted: `<CLAUDE_CODE_TMPDIR or /tmp>/claude-<uid>/<project>/<session id>/images/<N>.<png|jpg|gif|webp>`, <project> being the session's starting folder sanitised (hashed past 200 characters), which the mod doesn't rebuild: it looks for `<session id>/images` under each project folder. Read from the 2.1.311 binary and confirmed by a pty spike on 2026-10-27; it is not API, so a release may move it. `hooks/thumbs.ts` says where.
- `Image` takes PNG only, at most 2 MiB: a picture larger than 320 px or not a PNG goes through `sips -Z 320 -s format png` into `<session id>/paste-thumbnails/`. sips enlarges a small one to `-Z`'s size too, so a small PNG is sent as it is. The band's hooks run in install order, prompt-enhancer's above this one, so each band mod draws its row with `await next(e)` beside it rather than in its place: prompt-enhancer answering without `next` hid the thumbnails behind any draft. prompt-enhancer puts what is beneath above its row, so the thumbnails sit over ✨ Enhance.
- Claude Code draws an `Image` with kitty graphics only where XTVERSION names `kitty` or `ghostty` (or iTerm2 3.5+, fullscreen, bytes only). Mado answers `libghostty`, so there it draws the alt text (the pasted size) unless `CLAUDE_CODE_FORCE_TERMINAL_IMAGES=1`, which `~/.zshrc` exports in Mado shells. With it, the band sends the PNG in the stream with Unicode placeholders, the form Mado 0.3.0 draws; a spike confirmed the escapes, not the pixels in a Mado window.

## reply-style

- On the terminal, `AssistantMessage` and `CommandOutput` rows are parsed by `hooks/markdown.ts` (blocks, then inline runs) and drawn by `hooks/draw.tsx` with `Box`/`Text`/`Link`/`Code`; the built-in `Markdown` element takes no colours. The other surfaces, a summary row (`isSummary`), an errored or ANSI-coloured command output, and command output with no markdown in it (lines laid out by hand) go to `next`.
- The replacement row draws the engine's parts itself: `marginTop={1}` and the `⏺` bullet (on `isFirstOfReply`) for a reply, the `  ⎿  ` mark for command output. A pty spike on 2026-10-28 (pyte screen, haiku) matched the engine's spacing.
- Colours are theme keys, so they follow `/theme`. The Mado theme gives `warning` the accent's colour and `permission`, `ide` and `suggestion` one colour, so numbers are `merged` and paths `success`.
- Tables are wrapped by the mod, not the engine, so the borders stay whole: `widthOf` counts East Asian wide letters and emoji as two columns. Code uses the engine's `Code` highlighter, whose colours are the engine's.
- A bare URL is plain coloured text: a `Link` whose text is its address prints it twice in a terminal without OSC 8 links. A link that isn't `http(s)` is drawn as `text (target)`, never clickable.
- A fence tagged `copy` and a label (```` ```copy Slack reply to Hana ````) holds text the person pastes elsewhere. It is drawn as written, not read as markdown, beside a `suggestion` bar (not prompt-style's orange) under its label and a `[ copy ]` button that copies the text exactly. Code and copy blocks share one counter for their buttons' keys. A `prompt.compose` hook adds the rule in `hooks/copy.ts` as the last, `session`, section of the system prompt, except where nothing draws (`-p`) and under `--bare`. A pty spike on 2026-10-28 (haiku) confirmed that the model writes the fence for a Slack draft unprompted, and that a click on the button in fullscreen copies it: the engine ran the `pbcopy` it found first on `PATH`.
- Buttons in a transcript row take clicks only in fullscreen: outside it the terminal is sent no mouse modes (the same spike), so there `/reply-style copy [code|draft]` is the way: the last reply, or its last code or copy block.
- `/flash-copy` puts a letter before each copy button on screen, as flash.nvim's labels: `ctrl+x y` runs it, bound as `command:flash-copy` in the Chat context of `~/.claude/keybindings.json` (a `command:` binding takes a name, no arguments, and only in Chat). A reply row's `onScreen` (null when scrolled out) says which rows are on screen, the order each `requestId` was first drawn orders them, and the newest row's last button takes `a` (`hooks/flash.ts`). The letters live in the `hints` atom, which every reply row reads as it draws, so writing it redraws them.
- While hints are up the next `prompt.edit` is theirs: a hint's letter copies its block and is consumed (`{ text: e.text, cursor: e.cursor }`); any other key or cursor move takes them down and lands. Running the command again, or a submit, takes them down too; Esc is `chat:cancel`, not an edit, so it leaves them up. Outside fullscreen the rows above the prompt are never redrawn, so the command only says so. A pty spike on 2026-10-28 confirmed that the key runs the command with no transcript row and no record for the model, and that the letter copies, stays out of the box and leaves a draft there as it was.
- reply-style answers every terminal reply row without `next`, so another mod's `AssistantMessage` hook beneath it never runs there; installed mods sit in install order (see paste-thumbnails), and a `--plugin-dir` mod sat above it in the spike. Copy buttons on replies belong in this mod for that reason.
- The turn footer is left alone: `TurnDuration` props carry the word and duration but not the rest of the line (`· done 9:32 AM`), which a redraw would drop.

## walkthrough

- Claude hands over items to decide by calling `mcp__walkthrough__review_items` (`isDeferred: false`) with a title and 1–20 items: title, Markdown body, recommendation, at most 9 choices (one may be `recommended`), `multiSelect`, and a preview (`mermaid`, `markdown`, `code` or `diff`). `hooks/review.ts` checks the input and refuses a bad one saying what is wrong. The tool and `/walk` are registered only when `e.isInteractive`; a `prompt.compose` rule, last and `session`, says when to use the tool, except under `-p`, `--bare` or with nothing drawing.
- The tool answers at once and tells Claude to end its turn: a `tool.call` hook has 10 s of its own time, and `$.ui.ask` is the only call that waits for the person. Its transcript row lists the item titles with an open button; the result row draws nothing unless it errored.
- The pane (`walkthrough`, asked 96 × 40, so the dock's 45% caps it) shows one item. `j`/`k` walk the ring over the choices (on the summary, its items and Send); Space marks the choice under the ring (single: it is the answer; multi: toggle) and stays; Enter on a choice picks it (multi: keeps the marks, or takes this one when none is marked) and goes to the next unanswered item, as a digit does on a single-choice item only (on a multi-select one it would press the same Button as Enter). `h`/`l` go back and on, `w` focuses the Note field (an own answer with no pick, else a note), where Enter saves and Esc clears it and gives the keys back to the choices. `t` cycles picture → text → source, `v` opens the PNG with `/usr/bin/open`, `s` goes to the summary, where a digit jumps back and `s` sends. The review lives in `$.state` until sent; `/walk` opens it again and `/clear` drops it.
- A focused pane takes Tab, arrows, Enter, Esc and Button hotkeys (one digit or lowercase letter); any other printable key, Space included, moves the keys to the prompt box and arrives there as a `prompt.edit` with `key`. A `prompt.edit` hook keeps such a key out of the empty box when the pane held the keys or lost them within 200 ms (the render's `isFocused` flips after the edit), marks on Space, and on `$.clock.after(1)` gives the pane the keys back with `$.ui.open({ focus: true })`, which works only over an empty box; the ring then lands on the autoFocus choice, the one kept in the `cursor` atom. Esc in an Input gives the keys to the prompt with no event: a render with `isFocused` false while the ring is in the Note field is taken as Esc, so a click away from the field in fullscreen clears it too. The terminal empties an Input on Enter and puts back the drawn `value` only when it differs from the last, so the field is keyed `note-<saves>` and drawn afresh after each save. A mod's own `$.ui.focus` doesn't raise its own `ui.focus` hook, so the module keeps the ring itself. A pty spike on 2026-10-28 confirmed all of it in fullscreen and the classic layout. ctrl+x tab didn't give the keys to a pane that never had them (the tool opens it mid-turn, unfocused); `/walk` did.
- In `claude plugin test` the mod's own `$.ui.focus` has no implementation and throws, which the module reads as a refusal: the tests move the ring by raising `ui.focus` with origin `person` from the test's `$`, and raise `prompt.edit` the same way.
- Send closes the pane and, on `$.clock.after(1)` (the submit waits for the turn it starts), sends `Review answers · <title>` and a line per item through `$.prompt.submit({ asUser: true })`. The transcript labels it "Prompt from the walkthrough plugin". A dropped or refused submit puts the review back and says so in a toast.
- A hooks module has no Node, so `render/mermaid.mjs` runs under `node` through `$.process.run` with a JSON request on stdin. `render/vendor/beautiful-mermaid.mjs` is an esbuild bundle of beautiful-mermaid 1.1.3 with elkjs and entities; `render/vendor/LICENSES.md` has the build command and the licences (MIT, EPL-2.0, BSD-2). It draws box-drawing text (and a top-down copy of a left-right flowchart for a narrow pane) and an SVG that `rsvg-convert` (Homebrew's librsvg) turns into a PNG at 2× in the theme's colours, under `$TMPDIR/claude-walkthrough/<session>/<review>/`. rsvg-convert draws CSS `var()` colours black and ignores the stylesheet's font, so the script resolves the variables to hex and sets the font on the root `<svg>` first. Without rsvg-convert there is text only; without node, the source and why.
- A mod can't ask the terminal whether it draws images, so a review opens on the picture only where the environment suggests it does (`CLAUDE_CODE_FORCE_TERMINAL_IMAGES=1`, `KITTY_WINDOW_ID`, or `TERM_PROGRAM` `ghostty` or `iTerm.app`), else on the text. Pixels in a Mado window are unconfirmed; desktop, VS Code and mobile get the text.
- A pty spike on 2026-10-28 confirmed the whole flow with Sonnet, interactive and under `-p`: the tool called unprompted, the row, the docked pane, the keys, the summary and the answers reaching Claude. Haiku wrote the list in its reply instead, rule or not. The pane docks only in fullscreen, which a pty session gets with `CLAUDE_CODE_NO_FLICKER=1`; kitty graphics garble a pyte screen, so spike without forced images.

## restart

- Claude Code 2.1.312 ships `/restart` (alias `/update`): it replaces the process in place (`execve` of `~/.local/bin/claude --resume <id>` with the original flags), so it keeps the old environment, and it refuses while Remote Control is connected, which `remoteControlAtStartup` makes every session here. `$.command.register` refuses the name, but a `command.run` hook on `{ command: 'restart' }` answers in its place, `/update` included. The API has no call that ends or relaunches the process. A Mado spike on 2026-10-28 confirmed all of it.
- The hook reads what to restart (`plan` in `hooks/register.ts`): Claude Code's pid is a hook child's `$PPID`, the shell's is its parent's; `bin/argv.py` reads both argument vectors exactly (sysctl `KERN_PROCARGS2`, through `/usr/bin/python3`); `hooks/relaunch.ts` keeps the flags, read against `claude --help`'s option list, less those that pick a session or send a prompt (`-c`, `-r`, `--session-id`, `--fork-session`, `-p`, `-w`, a prompt word, ...). Before the session's first prompt there is no transcript, so the new one starts fresh. A parent that isn't a POSIX shell (`zsh`, `bash`, `sh`, ...), `--no-session-persistence`, or any failure hands over to the built-in with a dim line saying why; the hook's `.catch` does the same.
- It writes `$TMPDIR/claude-restart/<id>.sh` (remove itself, `cd` to `$.session.cwd()`, `command claude --resume <id> <flags>`, then `exec <shell> -l`), starts `bin/relaunch.sh` with `nohup … &` so it outlives the exit, and runs `$.command.run({ command: 'exit' })` on `$.clock.after(300)`. The helper waits up to 60 s for the pid to go, then types ` exec <shell> -l -i -c '. <file>'` into the pane's shell: the login shell reads its startup files again, so new and changed exports take effect (one removed from `~/.zshrc` stays, as `exec` keeps the shell's environment), and `claude` from `PATH` is the newest install. Its log is `$TMPDIR/claude-restart/<id>.log`.
- It types through `mado send --expect-fg <shell pid>` in a Mado pane (`mado locate --pid`), else with `bin/type.py`: TIOCSTI on the tty. The helper sits in Claude Code's process group, orphaned once it exits, and the terminal answers TIOCSTI from there with EIO; `type.py` joins the shell's group first. A Mado spike on 2026-10-28 restarted a session with Remote Control on through each path: same session id and conversation, the changed export read, the same pane and shell, about 4 s, and a login shell after the next exit.
